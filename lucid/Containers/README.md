### Allocation reservation and editing

New records store an exact private envelope in the same atomic UUID file:
`storageVersion: 1`, the unchanged version-1 `configuration`, and a strict
Boolean `allocationReserved`. Read/list and typed consumer replies still expose
the original configuration shape. An unreserved new record accepts exact
next-revision edits. Once reserved, **every** ordinary edit conflicts, including
a name-only change; the root store enforces this under `configuration.lock`.
The original complete candidate can still be read and reconciled, and an
already-saved typed create/update retry never rewrites or clears its reservation.

The allocator validates eligibility, current document, physical context,
inventory and aliases before atomically reserving the exact saved document,
then publishes allocation intent. A competing edit either commits first and
makes the reservation CAS conflict before intent, or sees the durable reservation
and is denied. The configuration lock's device/inode is pinned at store open;
the same held lock, directory and full on-disk envelope are rechecked around
publication and readback. A missing or substituted lock is not repaired.

`reserveConfigurationForClosedAllocation:beforeDeadline:error:` is a trusted
root-local helper inside the retained license owner's existing synchronous
source-operation fence. `sourceOperationCurrentBeforeDeadline:` verifies that
exact owner's queue, active fence, original deadline and live authorization.
The helper starts no nested operation and accepts no caller grant. The allocator
uses a separate read-only reservation assertion before resuming a journal and
at its final check, so verification cannot silently repair a downgraded marker.

A failed operation may already have reserved its document, even before an
allocation journal exists. Keep the same UUID and complete document, revalidate
and reconcile. Missing intent does not permit thawing or generating a successor
silently. No ordinary release, post-allocation editing, migration or identity
retirement policy is implemented by this boundary.

Legacy flat configurations remain readable, but their reservation state is
UNKNOWN and ordinary edits are denied. With no journal in its verified inventory,
the trusted allocator may conservatively reserve the exact selected legacy
document as true. A present journal requires an already strict true reservation;
false or legacy state refuses resume without conversion or repair. Quiesced
migration of old journals and mixed old/new allocator operation are unsupported.
This source policy is not installed owner UI integration or a customer upgrade.
Atomicity covers cooperating current-version store writers using the same
pinned lock; arbitrary root writes outside this protocol are not fenced.

## Original authenticated configuration consumer (historical boundary)

The current source service globally rejects this family's `prepare`, `create`
and `update` routes. Only `read` and `list` remain, through the root pending
context below. The following describes the earlier library and its recorded
acceptance, rather than the current service's mutation interface. The unit14
saved-setup form has not yet been adapted to the new root-owned protocol.

`LBXSendContainerRequest` sends the typed `container-configuration` IPC family
to the same build-pinned root service as licensing. The service checks the
client's exact executable path, size and SHA-256 against its kernel audit identity;
the client checks the root reply's audit identity and fixed service path. Caller
arguments cannot replace the endpoint, request UUID, deadline or authorization.
Unknown keys, malformed types, mismatched replies and late replies are rejected.

`prepare` accepts a name, requested app membership, complete manual identifiers
or a random choice, and a proxy reference. It returns a revision-1 document
without writing it. `create` saves that exact document. `update` carries the
complete expected prior document and its next revision. `read` returns one exact
saved document; `list` returns only UUID, revision, name and requested membership.
These payloads are private user data and must not be logged or exported as
diagnostics. Every reply reports `runtimeAccepted: false`.

`LBXContainerOwner` requires current source authorization for preparation,
inspection, saving and exact retries. Authorization derives from a fresh signed
production assessment committed by `LBXLicenseOwner`, lasts at most 60 seconds
and is bounded by signed expiry. A service restart starts closed even with a
saved pairing; online revalidation is required before configuration access.
Revocation denies access, including a retry of an already saved document.
The service opens existing configuration storage with `create:NO`; explicit
first-install directory/lock initialization remains required.

An identical already-persisted create or update returns the same document
without rewriting, changing its revision or regenerating identifiers. A
different stale edit returns `conflict`. A disconnected, unauthenticated or
late reply can return `unconfirmed`; this does not establish whether a write
committed. For every create/update result other than `saved`, retain the full
original candidate and UUID, including `authorization_required` after a failed
final fence check. Revalidate, read the original UUID and reconcile exact
durable state before deciding whether to resend that candidate in a fresh request.
Do not prepare a new random identity to retry an uncertain save.

The schema bounds requests to 16 KiB and replies to 64 KiB; the service also
bounds its incoming wire payload before decoding. Requests use a fresh UUID
and a 24-second deadline. List pages contain at most 40 ordered entries,
including valid Unicode names, with an exact last-UUID continuation cursor.
The underlying inventory remains bounded to 4,096 records.

## Mobile saved-setup mutation recovery (Unit 14 historical frontend)

`LBXContainerMutationCoordinator` connects saved source UUID setup metadata to
the fixed authenticated license/configuration clients. It does not operate the
owner engine's numeric container IDs, run an application or grant isolation.
Every configuration RPC is preceded by fresh website-backed source-license
validation. New creation prepares once, persists the full candidate, validates
again and sends that exact document. Editing starts from a full read record and retains the
exact expected document; list projections are never compare-and-swap authority.
Nil edit fields retain every existing identifier, including random choices.
Creation currently requires an empty proxy reference; no proxy resolver is
provided. All callbacks retain `runtimeAccepted=false`.

`LBXContainerPendingMutation` stores one private candidate/expected pair before
the first mutation send. Each stage/attempt carries a local UUID and monotonic
epoch/attempt counters. Atomic writes use the same pinned private lock and
compare the complete current state. Dismissal, transport timeout, process
restart, conflict and `authorization_required` after root publication cannot
discard unresolved work or silently prepare a new UUID. Startup only reads
pending state; it does not resend. The user can explicitly reconcile or retry
the same setup. An exact root read matching the candidate confirms it; a missing
create or an exact expected update keeps it retryable. Any other record, or a
missing update, remains a conflict with the full original candidate retained.
Retry validates, rereads and then validates again before sending the same
candidate and expected document. Missing/unsafe local state is unavailable,
never a verified empty slot. Late or duplicate callbacks cannot clear a changed
epoch or different pending document.

Only an exact `saved` reply or full `record` proof from the fixed authenticated
client permits local compare-and-swap clear. A local clear failure never reports
`saved`. Before publication it retains the durable slot; after publication it
may leave verified empty state because exact root proof already preceded the
clear. The coordinator retains that original candidate in memory and requires
fresh validation, an exact root read and verified local state for cleanup
reconciliation. A restart can safely observe already-proved empty state; no
second acknowledgement protocol is claimed. A verified different nonempty
slot supersedes old cleanup memory, preventing its later resurrection.

The production factory requires real and effective UID 501 and independently
observes the fixed compiled client executable and physical application home.
The established context binds their paths/file identities/digest and the fixed
source endpoints. It contains no credentials and proves neither root-service
pairing generation nor installation ownership across a root reset. A separate
trusted ownership/pairing policy is still required for those transitions. The
current recovered owner manager runs with real UID 501 and effective UID 0, so
this strict mobile factory refuses it; changing global process credentials or
relaxing that role is not part of this unit. A new source frontend also needs a
separately established fixed executable pin rather than a self-hash claim.

State lives under the fixed `Library/Application Support` private leaf, outside
Documents/export routes. Its separate establishment marker prevents an existing
missing leaf, state or lock from resetting as fresh. Directory descriptors,
parent/lock/file identities, ownership, 0700/0600 permissions, ACL absence and

duplicate-key representations. Private documents are bounded to 32 KiB and
