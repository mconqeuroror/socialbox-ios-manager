# Facebook private preferences and App Groups — FBSTORE-001 / FBSTORE-002

This implements a storage boundary for the audited Facebook **578.1.0 (1063022819)** source. It does not activate Facebook, authorize its network gate, manufacture identifiers, or establish complete Facebook account isolation. Production `runnable` and `defaults-wire` remain false. Existing Keychain ownership is still governed by FBKEY-001 through FBKEY-005.

## Boundary implemented

The four exact original App Group declarations are aliases, never added entitlements: `group.com.facebook.Facebook`, `group.com.facebook.family`, `group.com.metaplatforms.family`, and `group.com.facebook.msysstorage`. Each maps to a distinct role, respectively `app`, `family`, `meta-family`, and `msys`. The family and Facebook defaults suites have original-app runtime evidence; the other two are binary-declared groups. See [binary audit](facebook-binary-audit.md) and [runtime observations](facebook-runtime-observations.md).

Preferences map each role to `<validated-clone-bundle>.sbx-storage.v1.<role>`. The source application domain maps to the clone bundle. Already-mapped own domains are idempotent. Foreign clone domains, unknown groups, prefix extensions and malformed inputs fail closed without a retry against the original provider. Standard defaults keep their native semantics. Keys, opaque values, data, dates, dictionaries, arrays and type/validity results are preserved; no random identity substitution occurs.

Nine Foundation selectors cover suite initialization/search-list changes and persistent/volatile domain read/write/removal. Fourteen CFPreferences entrypoints cover scalar, typed, bulk, key-list, synchronization, suite-list and forced-value APIs. Explicit CF owners are limited to current user with current/any host. Platform/global preferences remain shared native read surfaces; they are **not claimed as private device identities**. Explicit persistent platform writes and writable platform suite construction are rejected. Domain-name enumeration and native global settings still require separate threat assessment.

`containerURLForSecurityApplicationGroupIdentifier:` maps each exact group into the current OS clone home's `Library/Application Support/SocialBox/PrivateGroups-v1/<role>`. Directories are created mode 0700. Component-by-component `openat` with `O_NOFOLLOW` rejects symlinks and non-directories; existing parent permissions are not modified and every traversed child must have the caller's uid. Unknown groups return nil. This adds no original App Group entitlement and does not activate legacy path rewriting. Isolation against sibling sandboxed apps relies on the separate OS-issued homes; it is not protection against root or a compromised jailbreak.

The installer requires a validated Facebook profile, exact container-derived bundle and complete Keychain metadata, enabled descriptor, and matching audited source/runtime versions. Binding is immutable and serialized; readiness is atomically published only after checked installation. Failed installation cannot be layered with a retry. The extra `facebook-storage` self-report is installation evidence, not admission to network access. Reddit never invokes this installer.

## Executable verification

- `tools/test_facebook_storage_policy.sh`: **50** assertions. The initial missing-policy test failed compilation before implementation. Exact roles, separate A/B namespaces, idempotence, foreign/malformed domain rejection and legacy Reddit exclusion.
- `tools/test_facebook_private_group_store.sh`: **42** assertions using real temporary files: four separate directories, repeat resolution, A/B marker separation, permissions, unknown groups, path injection, symbolic links and non-directory denial.
- `tools/test_facebook_storage_hooks.py`: **238** assertions across 13 fresh processes, including **154** on the active path. Compiles the actual Logos output, really swizzles Foundation, and invokes actual C wrappers against native CFPreferences with an inert C patcher. Tests exact opaque-value preservation, typed/bulk/removal/sync semantics, native suite search, foreign canaries and denied mutations, platform suite rejection, invalid owners/versions/profile/group metadata, inactive production and failed installation. The enabled registry exists only in a temporary fixture directory.
- Physical iPhone 8 / iOS 16.7.16: the preceding native-wrapper fixture passed **153** checks before the final platform-suite tightening; the filesystem fixture passed **42**. These are diagnostic helper checks, not sandboxed Facebook launches.
- Final physical probe uses **real Substrate** C and Objective-C hooks, the actual compiled installer, public APIs and seeded synthetic data. **22 seed + 97 verification + 13 cleanup checks passed**. It verifies Foundation/CF interoperability, unchanged opaque bytes, foreign-canary denial, four distinct same-key values, platform-suite denial, and actual group URL interception. All test canaries and temporary group files were removed. Source/binary and log hashes are in [device evidence](release-evidence/facebook-storage-device-0.1.29.json).

Reproduce the physical probe by setting `THEOS` and running `python3 tools/build_facebook_storage_device_probe.py <private-output-directory>`. Sign `probe` with Procursus ldid using the emitted synthetic entitlements. Run `probe seed <fresh-32-hex-nonce>`, then `probe verify <same-nonce>`, and always `probe clean <same-nonce>` in a separate process. The builder never changes the production registry or installs anything. The helper uses synthetic data and a temporary home for group tests; it does **not** impersonate a complete sandboxed clone or exercise real Facebook accounts.

## Remaining acceptance boundaries

Actual paired Facebook clone probes were subsequently run: they exposed cross-container filesystem reads and an app-startup failure. See [actual device acceptance](facebook-clone-device-acceptance.md). SDK coverage and stable first-use execution remain incomplete. Unknown suites deliberately fail closed and may reveal compatibility gaps during those launches. The observed calls and successful helper tests do not prove every Facebook private storage implementation passes through these APIs. File access outside the group URL API, WebKit, existing Keychain wrappers, custom transports, runtime readiness and OS sandbox entitlements still require their own acceptance evidence.

Backup/restore into a **new bundle** needs explicit migration of the old clone's preference filenames/domains and observed SDK restore behavior; this change does not rewrite archives or claim login preservation. Private group role paths are stable inside the home, but file-copy success alone is not login restoration. See [backup integration limits](facebook-backup-integration.md). Network enforcement remains separately unverified, so this unit must not enable Facebook traffic. The broader FBRUN rows remain open.
