# No-MDM network enforcement: implementation decision and observed capability

The connected iPhone supports a root, read-only PF status query. This makes a **device-wide proxy-only firewall** a concrete candidate that can reuse SocialBox's existing HTTP proxy hooks, without MDM or a new TCP/IP stack. No filtering rule has been installed or measured. This is a capability result, not permission to open the production network gate.

## What the phone actually proved

On iPhone10,6, iOS 16.7.16, palera1n rootless, Darwin 22.6.0 / XNU 8796.142.1.703.8, the independently built diagnostic opened `/dev/pf` read-only and successfully executed `DIOCGETSTATUS` as root. The 440-byte arm64 status record reported PF disabled, zero states and zero source nodes. The [sanitized receipt](release-evidence/no-mdm-pf-capability-2026-09-20.json) records the source/binary hashes and exact scope.

The diagnostic is [tools/pf_readonly_probe.c](../tools/pf_readonly_probe.c). It enumerates interface names, reads the kernel version and reads PF status. It contains no rule, route, preference or packet-writing operation. Its ioctl layout was checked against [Apple's XNU PF interface](https://github.com/apple-oss-distributions/xnu/blob/xnu-8796.121.2/bsd/net/pfvar.h); its successful return confirms this status ABI on the tested later kernel. The [kernel implementation](https://github.com/apple-oss-distributions/xnu/blob/xnu-8796.121.2/bsd/net/pf_ioctl.c) requires root for the query. Device-node presence alone was not counted as a successful capability test.

The probe needed an explicit empty entitlement plist signed by Procursus ldid, including DER entitlement slots. Execution in `/var/mobile` was killed before output; the same signed bytes executed from the diagnostic directory under `/var/jb/usr/local/libexec`. No system trust configuration was changed. The exact reason for the path-dependent startup remains unproven.

There is no installed `pfctl`, and the current local apt-cache lists no `pfctl` candidate. That is a tooling gap, not proof that kernel PF filtering is unavailable. No live rule load or traffic capture was attempted. Existing reference-product daemons and hooks are active on this phone; they must not be counted as SocialBox protection.

### Completed rule, anchor and state inspection

The separate [PF inventory helper](../tools/pf_readonly_inventory.c) subsequently ran as root from the bootstrap diagnostic directory and exited zero. It issued 19 read-only queries: PF remained disabled, all six root ruleset families were empty, there were no child anchors, and the state snapshot was empty. The before/after policy checksum was unchanged. The original status-only probe and its receipt/hash are preserved. The [inventory receipt](release-evidence/no-mdm-readonly-inventory-2026-09-20.json) records the distinct helper and private result hashes.

The helper recursively enumerates anchors and the scrub, filter, NAT, BINAT, RDR/NAT64 and dummynet families, validates rule tickets before/after enumeration and checks state-buffer lengths and growth. It has explicit query, depth, count, memory and time bounds. Unsupported ABI fields or a detected concurrent change make the result incomplete; they are never silently interpreted as an empty policy. The ioctl whitelist additionally rejects `DIOCGETRULE` with the counter-reset action. A read-only file descriptor alone is insufficient: Apple's implementation allows some mutating PF commands through that descriptor.

The public `pfvar.h` files in Apple tags `xnu-8796.121.2` and `xnu-8796.141.3` are byte-identical. **112 size/offset/ioctl assertions** compile against the pinned header using both the Mac and arm64-iOS compilers. The phone's exact `.142.1.703.8` source tag is not published in that repository. Runtime evidence confirms the queries actually performed; because the phone had no rules or child anchors, `DIOCGETRULE`, `DIOCGETRULESET` and non-empty rule/state decoding remain **host-fixture tested, not exercised against live kernel entries**.

**132 behavioral checks** run the actual helper with a mocked ioctl boundary under ASan/UBSan. They cover recursive enumeration, IPv4/IPv6, packed unaligned counters and ports, no kernel-pointer serialization, denied mutation/counter reset, malformed records, overflow, truncation and concurrent changes. The inventory deliberately does not expand dynamic table entries or route/NAT pool membership, is not an atomic snapshot and cannot be restored as a firewall configuration. `enumerationComplete` means that its bounded enumeration completed; `enforcementVerified` remains false.

### Phone connectivity diagnosis

The independent [network probe](../tools/network_readonly_probe.c) reads interface flags and IP scopes with `getifaddrs`, then reads the default-route inventory using `sysctl` with `newp=NULL`. It performs no DNS requests or network connections, reads no saved Wi-Fi data, omits MAC identifiers and changes no radios or routes. **176 host checks** cover route parsing bounds, default-route recognition, reject/blackhole flags and address classification under ASan/UBSan. The 92-byte routing-message layout is included in the pinned Apple ABI checks.

The first complete phone snapshot had **zero up non-link-local IPv4 addresses, zero up non-link-local IPv6 addresses and zero IPv4 default routes**. Its five IPv6 defaults were scoped to `utun0`–`utun4`, whose observed IPv6 addresses were link-local; 61 route records were inspected. Combined with the separately observed `NSURLErrorNotConnectedToInternet` from the actual daemon proxy test and failure to resolve the existing licensing host, this supports a missing normal Internet uplink at that observation. It does **not** establish a bad proxy credential, prove the DNS server configuration itself is defective, or identify who changed connectivity. The probe itself does not test Internet reachability. Raw address-bearing output stays outside the repository; only sanitized counts, flags and hashes belong in the receipt.

The final flags-complete snapshot exited zero and retained those same counts. `en0` had UP and RUNNING flags but **no IPv4/IPv6 address**; `pdp_ip0`–`pdp_ip4` were neither UP nor RUNNING. Thus “Wi-Fi is switched off” is not established: a present/up interface without an address is different from an administratively down interface. The next online acceptance attempt needs a working uplink and a fresh route/proxy test. Neither diagnostic changed radio state or attempted to fix networking behind the user's back.

## Why the current provider cannot simply be enabled

The shipped `PacketTunnelProvider` is an `NEAppProxyProvider`, despite its historical filename. Its host uses `NEAppProxyProviderManager.loadAllFromPreferences`, expects a managed per-app configuration, and the provider admits `NEAppProxyFlow` objects only when their signing identifier matches the active lease. `TCPRelay` consumes stream flows, not IP packets. `RBXNetworkGate` and the tweak both require a fresh `transport=app-proxy`, `scope=per-app` receipt. Changing those strings would erase the evidence boundary rather than implement an alternative.

Apple's [deployment requirements](https://developer.apple.com/documentation/technotes/tn3134-network-extension-provider-deployment) distinguish unmanaged packet tunnels from managed app proxies. Its [manager documentation](https://developer.apple.com/documentation/networkextension/netunnelprovidermanager) describes the MDM-created app rules needed for public per-app routing. This review did not establish a supported local replacement for those rules on iOS.

The read-only [reference-product findings](doritoz-device-reference-2026-09-19.md) establish a packet-tunnel/local-proxy implementation family. They do not prove its route exclusions, IPv6 handling, provider-death behavior or independent per-app attribution. None of its code or assets are used here.

## Smallest PF implementation units

1. **A capability and policy-inspection helper — bounded inspection implemented.** The helpers above now bind their runtime to the observed kernel, enumerate existing rules/anchors/states and report unsupported data honestly. A future writer additionally needs expanded address-table/pool inspection and a preservation strategy for non-empty system policies; the current empty phone snapshot does not prove that future snapshots will remain empty. No existing anchors may be overwritten or cleared.
2. **A separately named device-wide backend.** Generate a bounded policy that covers IPv4 and IPv6 and allows only the configured numeric HTTP proxy endpoint and necessary, precisely scoped management traffic. Unknown protocols, direct DNS, UDP/QUIC and unrelated destinations remain denied. Existing HTTP/CONNECT hooks can then use their normal proxy endpoint. Do not open general cloud/rotation destination exceptions to app traffic or allow every root process: brokered requests could use those exceptions. Prefer control requests through the authorized proxy, with a separately reviewed bootstrap/rotation design. USB recovery access requires its own reviewed tuple/interface exception and threat-model limitation, not a general local-network pass rule.
3. **A kernel policy transaction and recovery protocol.** Establish a dedicated deny policy before any app launch, verify the active rules/anchor ordering and policy digest, remove prior admitted states, and only then acknowledge admission. An old established PF state can survive a rule change; merely publishing a new rule list is not revocation. Failures retain deny and preserve the pre-existing system policy. Rollback must never restore broad network access while a selected app can still execute. Build a reviewed local recovery mechanism before a live experiment that could sever SSH.
4. **A separate assurance receipt and lifecycle integration.** This mode is `device-proxy-only`, not `per-app`. PF does not supply the exact source-app signing identity used by the current provider. Ordinary apps share UID 501; UID matching does not identify a clone. Existing exact-container lease hooks, process termination and operation journals remain required. A static kernel allowlist continues to prevent direct egress after daemon death, but its OPEN allowance does not naturally expire with a plist heartbeat. Selected-container-only authorization and expiration therefore require an independently tested revoker/supervisor and unsolicited-launch tests. Do not re-use the current provider's green receipt.
5. **Measured acceptance before integration is enabled.** First use disposable synthetic clients and a controlled destination, with capture independent of the reference hooks. Exercise IPv4 and IPv6, interface-bound sockets, existing connections, DNS/DoH/DoT paths, UDP/QUIC, daemon/revoker death, delayed callbacks, proxy failure, rapid A/B switches, network handoff and reboot. Check exact proxy destination and physical egress, not only a displayed exit-IP address. Then repeat inside actual app processes and prove old/background/unselected clones cannot continue under the selected proxy.

Units 2–5 still require implementation and physical acceptance; a rule string generator and mocked success cannot establish a kernel-enforced backend. No production backend, alternate readiness receipt or network admission change is included in this feasibility work. The absence of MDM is no longer the only unexplored path, but it is still a blocker for the currently shipped app-proxy mode.

### Reproducing the read-only checks

Run `python3 tools/test_pf_readonly_inventory.py` and `bash tools/test_network_readonly_probe.sh` on a Mac with Xcode. Acquire the four pinned Apple headers listed in `tools/test_pf_readonly_abi.py` from `apple-oss-distributions/xnu` tag `xnu-8796.141.3`, preserving the `libkern/tree.h` and `net/radix.h` relative paths, then run `python3 tools/test_pf_readonly_abi.py --headers <directory>`. That script verifies header hashes and both compiler layouts; it makes no downloads and does not access a device.

Each diagnostic is a standalone C file compiled with `xcrun --sdk iphoneos clang -target arm64-apple-ios15.0 -Wall -Wextra -Werror -O2`. Sign the resulting binary using the explicit Procursus ldid path and an empty entitlement plist; verify code-page, XML and DER hashes before transfer. These diagnostics are not package daemons and are not linked into the launcher, tweak or network provider. They accept no command-line mutation options. The network helper uses only the public route-message record shape from [Apple's header](https://github.com/apple-oss-distributions/xnu/blob/xnu-8796.141.3/bsd/net/route.h) and the 32-bit sockaddr alignment used by [its route exporter](https://github.com/apple-oss-distributions/xnu/blob/xnu-8796.141.3/bsd/net/rtsock.c).

## Packet-tunnel fallback if PF is unsuitable

A personal `NETunnelProviderManager` / `NEPacketTunnelProvider` is a public no-MDM alternative. It needs a separate extension identity, local configuration and a real IP-packet-to-TCP bridge. The existing app-proxy relay cannot be attached to `packetFlow` unchanged. A candidate such as [tun2proxy](https://github.com/tun2proxy/tun2proxy) documents iOS, HTTP proxy and IPv6 support under MIT; its dependency licenses, pinned version, packet parsing, bounded resources and integration would still require review. It has not been imported into this repository.

For this iOS 16 device, the SDK declares `includeAllNetworks` since iOS 14 and `enforceRoutes` since iOS 14.2; `excludeAPNs` and `excludeCellularServices` are available since iOS 16.4. Explicitly disable the optional exclusions, provide both IP families and test on-demand restart behavior. Default routes alone do not establish confinement against interface-scoped connections. [Apple's routing documentation](https://developer.apple.com/documentation/networkextension/routing-your-vpn-network-traffic) also lists unavoidable operating-system exclusions. They must be recorded rather than described as literal all-packet isolation.

A destination-based packet tunnel lacks app identity metadata and affects the whole device. Its host authorization, jailbreak signing, provider death, upgrade and recovery behavior need physical tests. [Mullvad's implementation report](https://mullvad.net/en/blog/why-we-still-dont-use-includeallnetworks) describes an update/connectivity failure with `includeAllNetworks`; this is a concrete recovery test requirement, not a claim that the same failure was reproduced here. A drop-only capability prototype can test routing first, but does not provide working proxy transport.

## Offline evidence that does not depend on MDM

The signed SocialBox package, launcher startup, licensing state, source validation/import, prepare/review/cancel creation, exact metadata, selection persistence, recovery journals and hidden-icon registration can be checked while traffic remains CLOSED. Disposable A/B app processes can exercise known-present Keychain, preferences, pasteboard and filesystem canaries with radios disconnected. A root helper reading data is not a substitute for in-app probes.

Prior [actual Facebook-clone acceptance](facebook-clone-device-acceptance.md) found cross-container filesystem reads despite a helper-only PASS. Repeat that in-process test after the relevant fixes; do not replace its FAIL with a successful installation or a network capability query. Restored logins and app usability are separate online acceptance items. Neither PF nor a VPN solves a filesystem isolation defect or server-side account correlation.

## Narrow shipping fix from this review

`FirewallPolicy` previously admitted a finite current time with `expiresAt=+infinity`, unlike the tweak's finite-expiry check. A regression failed first at that input. The provider now requires finite current time, heartbeat and expiry; seven nonfinite edge assertions and the original policy/DNS tests pass. `tools/static_check.py` is clean. This closes a malformed-lease acceptance discrepancy under **NET-036**. It does not provide MDM-free enforcement or alter any physical-network verdict.
