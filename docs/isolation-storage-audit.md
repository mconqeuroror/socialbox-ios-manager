# Active storage and sentinel audit

This bounded review found diagnostic false-PASS paths and exception paths that discarded positive visibility evidence. It tightened the evidence requirements and preserves observations already made. It does not establish a physical cross-container data leak, complete Keychain/defaults isolation or Facebook runtime readiness. Facebook remains inactive. Entitlements, storage remapping, network policy and account flows were not changed by this unit.

## Findings and correction

1. **Historical Keychain seed receipt was treated as current item existence.** `RBXSentinelTarget` in [RBXSentinelController.m](../daemon/RBXSentinelController.m) freshly checks a filesystem marker and a defaults plist, but its Keychain claim comes from a seed receipt up to an hour old. It cannot directly read another clone's Keychain to confirm continuity. The probe previously accepted `errSecItemNotFound` as PASS under this fresh `witnessAt`, even if the source item had subsequently disappeared. The new regression failed first at this case. The [probe](../shared/RBXIsolationSentinel.h) now records not-found as **NOT_RUN/inconclusive**. An explicit foreign-group `errSecMissingEntitlement` remains a bounded **PASS for access denial**, with the existing seed/witness prerequisites. Any successful canary lookup remains **LEAK**, regardless of returned bytes. The separate SSH A → B → A acceptance sequence can establish sampled continuity; this periodic sentinel does not perform that sequence.

2. **Empty clipboard was accepted without an independent marker.** The observer previously returned PASS whenever its public general-pasteboard reads were empty. That result also occurs when the clipboard was genuinely empty and isolation was absent. The optional own-marker write returning no visible content likewise did not prove that the write reached shared storage or that a sibling marker was hidden. Both outcomes now remain **NOT_RUN**. Visible content under the explicitly blocked clipboard policy still reports **LEAK**. Shared-clipboard compatibility remains NOT_RUN for isolation, and a nil/unavailable board is inconclusive. This does not change the blocking clipboard hooks or add routine clipboard writes.

3. **A nil defaults receiver could masquerade as absent data.** Objective-C messages to nil would return nil through `addSuiteNamed:`/`objectForKey:` and produce an absent-key PASS. The actual suite-read helper now rejects a nil receiver, propagates query exceptions to NOT_RUN, and removes the temporary suite in `@finally`. Tests exercise that helper with an inert API receiver, including cleanup after an exception. A non-nil receiver returning no value remains an **absent observation**, not a claim of an explicit permission denial. Its bounded PASS still requires the daemon's recent exact defaults-marker witness.

4. **Absence and permission denial were conflated in filesystem detail.** `ENOENT`/Foundation missing-file errors are now described as **absent**; `EACCES`, `EPERM` and Foundation no-permission errors as **denied**; nil or other errors as **unknown**. Unknown/error outcomes cannot pass. Successful foreign directory metadata or a read handle still reports LEAK under the stated visibility probe. The scope is the constructed directory/marker path through these Foundation APIs, not arbitrary file descriptors, raw syscalls or every SDK store.

5. **A later exception could erase an observed LEAK.** Three failing-first regressions reproduced this. Foreign directory metadata was observed, but a later read-handle probe threw; a foreign defaults value was returned, but suite removal threw; and the public Foundation factory opened a foreign file handle, but `closeFile` threw before the adapter returned success. These outcomes formerly became NOT_RUN and did not raise the sentinel alert. The filesystem probe now retains positive observations across later failures. The defaults helper always attempts suite removal and returns a value already read even if cleanup fails; no value plus cleanup failure still becomes NOT_RUN. The runtime file-handle adapter uses a shared helper that always attempts closing a received handle and preserves its successful open as LEAK even if closing throws. Tests use inert defaults and file-handle API receivers; they allocate no real descriptor, access no sibling files and write no sibling state. Cleanup is attempted once; the sentinel does not reopen or retry a foreign handle after an exception.

After existing structural/process validation, the daemon normalizes success classifications unsupported by the current probe policy to NOT_RUN. It preserves every LEAK row and does not mutate the stored receipt. A mixed-old-report regression failed first when strict PASS rejection discarded a valid LEAK; normalization now preserves that finding for the existing durable-alert path. Foreign/unbound, malformed, incomplete, duplicate or stale reports still fail validation. The existing daemon reads the stored alert flag or durable alert ledger before checking a report and only writes the flag to true. Any NOT_RUN prevents its all-rows-PASS summary. [RBXLaunchSafety.h](../shared/RBXLaunchSafety.h) separately retains the launch block; disabling the observer is not an acknowledgement or reset.

## Active storage paths inspected

- **Keychain:** [RedditBox.xm](../tweak/RedditBox.xm) calls `RBXInstallKeychainSyncPolicy`, not the dormant legacy namespace installer. [RBXKeychainHooks.xm](../tweak/Container/RBXKeychainHooks.xm) actively wraps SecItem add/copy/update/delete only for the optional local-only synchronizable policy. [RBXKeychainSyncPolicy.h](../shared/RBXKeychainSyncPolicy.h) changes only an explicit synchronizable true/Any selector to false and never broadens or retries a query. Existing exact clone-group entitlements remain the boundary. SecKey creation, persistent-reference semantics and all item classes still require native device acceptance; host dictionary tests do not prove securityd isolation. The known Facebook multi-group/key-class blocker remains in the [boundary plan](facebook-keychain-boundary-plan.md).
- **Defaults/CFPreferences:** the broad isolated-defaults and CFPreferences functions still present in [RBXRedditAPIHooks.xm](../tweak/Network/RBXRedditAPIHooks.xm) are not installed. The active Reddit installer installs request adapters and relies on the clone's OS storage boundary for defaults. The sentinel tests one exact seeded key via `addSuiteNamed:` plus `objectForKey:`. It does not cover `initWithSuiteName:`, persistent-domain/bulk APIs, direct CFPreferences, identical SDK suite names, source App Groups or arbitrary filesystem access. Those paths remain unverified until deliberate A/B tests establish their actual behavior.
- **Clipboard:** [RBXPasteboardHooks.xm](../tweak/Container/RBXPasteboardHooks.xm) blocks the public factories and instance API, mirrors blocking methods onto the observed general-pasteboard class-cluster subclass, and verifies the blocking behavior. Explicit system-clipboard compatibility instead preserves the original factory and disables the isolation claim. The SDK selector checker finds all 53 public entry points represented. This is source/API coverage and installation evidence, not a complete runtime proof for private interfaces, pre-existing objects or arbitrary future subclasses.
- **Web/cloud storage:** [RBXWebStorageHooks.xm](../tweak/Container/RBXWebStorageHooks.xm) includes ubiquitous-key-value-store blocking and ephemeral external-auth preferences. WebKit/cache/cookie isolation is primarily the cloned OS sandbox and signing policy. Neither the sentinel nor these host tests establishes every WebKit data store, broker, cloud metadata or callback boundary. No broad remapper was enabled to conceal that gap.

## Validation and operator interpretation

The failing-first sentinel run reported `FAIL: not-found cannot prove isolation from a historical Keychain seed receipt`. The exception regressions separately failed when a later filesystem exception, defaults cleanup exception or read-handle close exception erased positive evidence. After correction, the suite passes historical-seed absence, explicit group denial, unknown Security/filesystem errors, nil defaults receiver, suite cleanup on exception, positive observations followed by exceptions, negative observations with cleanup failure, empty/shared/unavailable clipboard, optional challenge classification, stale/process-bound receipts and unsupported PASS cases.

The pre-existing no-authentication-UI Keychain selector emits an SDK deprecation warning; these checks are not device acceptance results.

In the morning, treat NOT_RUN as missing/inconclusive evidence, not “safe” or a newly proven leak. Preserve any LEAK alert and collect its scoped metadata before further launches. Use the existing deliberate SSH canary sequence to seed A, verify B and return to A for continuity/cleanup; current helpers are Reddit-specific. Real Keychain class/reference/default-group behavior, all relevant defaults API paths, original/sibling group denial and clipboard A/B witnesses remain required. Do not use production account items, copy secrets into logs, clear alerts merely to continue, or enable Facebook as a diagnostic shortcut.
